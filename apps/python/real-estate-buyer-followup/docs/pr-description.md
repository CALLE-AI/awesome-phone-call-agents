# Real Estate Buyer Follow\-up Agent

**基于 CALL\-E 的上下文驱动型房地产客户跟进 Agent**

> 让 AI 电话不再是孤立的一次性对话，而是能够理解客户上下文、自主规划沟通、沉淀业务记忆，并逐步推动客户跟进目标的智能 Agent。
>
>

## 1\. 对 CALL\-E 及社区当前阶段的理解

我理解 CALL\-E 的核心价值，是为开发者提供 AI 电话交互与任务执行的基础能力，降低构建电话 Agent 的门槛。

但在真实业务场景中，能够完成一通电话，只是业务 Agent 的起点。

例如房地产客户跟进，一次有效的回访不仅需要自然地与客户沟通，还需要理解客户的购房需求、历史沟通、已看房源以及经纪人本次希望完成的业务目标。

电话结束后，新获得的信息也不应该只停留在通话记录中，而应该更新客户的业务上下文，成为后续跟进的依据。

因此，我认为 CALL\-E 社区除了展示电话能力本身，也适合通过具体行业案例探索：

- 如何将业务系统中的上下文转化为可执行的电话任务。

- 如何让 Agent 根据业务目标自主规划，而不是依赖固定话术。

- 如何让电话结果形成结构化业务数据和后续行动。

- 如何在真实世界副作用、业务约束和 Agent 自主性之间建立合理边界。

本项目希望提供这样一个行业应用示例，而不是重新实现 CALL\-E 的底层电话能力。

## 2\. 发现的问题与机会

### 2\.1 电话任务与业务上下文容易脱节

在常见的电话自动化方式中，开发者往往直接提供一段任务描述或固定话术，再让 AI 执行电话。

但实际业务信息通常分散在不同位置：

- CRM 中的客户画像与需求。

- 历史沟通记录。

- 已完成的看房记录。

- 房源资料及业务状态。

- 经纪人积累的专业知识与操作规范。

如果缺少上下文整合，Agent 就可能重复询问已知信息、忽略客户偏好的变化，或无法围绕本次业务目标进行有效沟通。

### 2\.2 电话规划缺乏自主性和可见性

经纪人真正关心的是业务目标，例如：

“帮我回访张女士，了解她对上次两套房源的看法，并判断下一步应该如何跟进。”

经纪人不应该需要亲自编写完整提示词、逐项配置问题和沟通顺序。

与此同时，真实业务中的电话又存在一定风险。经纪人需要在电话开始前知道 Agent 准备做什么、会依据哪些信息沟通、有哪些执行边界。

因此，这里存在一个产品机会：

**让 Agent 自主生成电话计划，同时让业务人员能够理解和确认计划，而不是要求业务人员代替 Agent 进行规划。**

### 2\.3 电话结果没有自然转化为持续跟进能力

客户需求通常不是一次沟通就能确定的。

例如：

第一次沟通，客户希望预算不超过 500 万、地铁步行 10 分钟内。

看房后，客户可能发现客厅空间比地铁距离更重要。

下一次推荐房源时，如果 Agent 仍然使用最初的偏好，就无法体现此前沟通的价值。

因此，我希望将每次电话视为持续客户跟进中的一次状态更新：

**已有上下文 → 自主规划 → 电话执行 → 结构化反馈 → 更新业务记忆 → 下一次跟进。**

这也是本项目最终希望探索的方向。

## 3\. 目标用户与业务价值

### 3\.1 目标用户

本项目主要面向房地产经纪人及需要持续跟进客户的房产服务团队。

典型场景是经纪人完成带看后，需要逐一联系客户，了解真实反馈、识别购房顾虑、确认需求变化，并安排下一步行动。

### 3\.2 为什么值得解决

房地产客户跟进具有几个特点：

1. **上下文丰富**：客户需求、历史沟通、房源和带看记录会持续积累。

2. **沟通目标动态变化**：不同客户、不同阶段，需要了解的信息并不相同。

3. **业务周期较长**：通常需要多次沟通才能推进到复看、议价或成交。

4. **人机协作边界明确**：AI 可以承担信息收集和初步分析，但关键交易决策仍需要经纪人。

因此，该场景适合验证上下文驱动、自主规划和跨会话持续跟进的 Agent 设计。

### 3\.3 预期价值

**对经纪人：**

减少重复回访准备、通话信息整理和客户档案维护工作，让经纪人将更多时间投入到高意向客户的服务、复看、议价与成交环节。

**对客户：**

减少重复解释需求，让每次沟通更有针对性，并使后续推荐能够参考此前真实反馈。

**对开发者社区：**

提供一个从业务上下文到电话任务、再到结构化结果处理的完整示例，展示如何在 CALL\-E 之上构建具有业务智能的 Agent。

这些属于项目希望验证的价值方向，当前尚未通过真实业务数据证明效率或转化率提升。

## 4\. 当前方案与贡献形式

### 4\.1 项目定位

本项目是一个基于 CALL\-E 的房地产客户跟进 Agent 社区示例。

目前使用**模拟 CRM 数据、业务知识库和演示工作流**，重点验证 Agent 如何整合上下文、自主规划通话，并将结果转化为可追溯的业务更新。

当前没有完成真实房地产 CRM 的生产级集成，也不以 CRM API 接入本身作为主要创新点。

真正希望展示的是：

**即使底层电话能力相同，不同的上下文组织、任务规划和结果处理方式，也会显著改变业务 Agent 的工作模式。**

### 4\.2 当前四阶段流程

#### 阶段一：Context Integration — 业务上下文整合

系统提供模拟 CRM 中的多类业务信息：

- 客户画像：购房预算、区域、户型、偏好等。

- 历史沟通：客户曾经表达的需求及其变化。

- 带看记录：客户已经参观过哪些房源。

- 房源信息：价格、户型、面积、交通等资料。

- 业务知识库：房源补充说明、看房回访 SOP、客户反馈分析规则等。

- 经纪人任务：本次希望 Agent 完成的具体业务目标。

这些信息具有不同的来源和作用。

CRM 主要提供客户和业务事实；知识库补充专业知识、操作规则和业务判断依据；经纪人输入本次目标。

Agent 不应简单将所有原始信息拼接到提示词中，而是根据任务筛选、整合和组织相关上下文。

界面支持查看信息来源，便于核对原始业务记录。

#### 阶段二：Autonomous Planning — 自主生成通话计划

经纪人输入业务目标后，Agent 根据整合后的上下文生成准备交给 CALL\-E 的通话任务。

当前规划内容包括：

- **任务目标**：本次电话需要完成什么。

- **组织化通话上下文**：哪些客户背景、历史偏好和房源信息与本次沟通相关。

- **规划沟通内容**：重点了解哪些问题，以及如何根据客户回答进行追问。

- **执行策略与边界**：避免重复提问，不擅自承诺价格、政策、预约或交易条件。

- **预期输出**：需要收集哪些结构化反馈，以支持后续业务处理。

以张女士的带看回访为例：

Agent 知道客户此前看过两套房源，历史记录显示她逐渐更重视客厅空间，而其中一套房源又超出了初始预算。

因此，Agent 可以自主规划：

1. 分别了解两套房源的实际满意点和顾虑。

2. 结合反馈判断空间、预算和交通之间的取舍。

3. 在有必要时确认预算约束是否变化。

4. 了解客户是否愿意继续看房，以及是否需要经纪人跟进。

这里规划的是**沟通目标与策略，而不是必须逐字执行的固定问题清单**。

经纪人能够在页面中看到 Agent 准备执行的任务，并决定批准或提出简要修改意见。

我没有将逐题编辑、逐项勾选作为主要交互，因为那会让经纪人重新承担 Agent 本应完成的规划工作。

#### 阶段三：Call Execution — CALL\-E 电话执行

通话计划经确认后，进入 CALL\-E 执行环节。

该阶段负责将准备好的任务交给电话执行能力，并展示通话任务状态和可获取的执行结果。

项目采用模拟通话作为安全演示路径，避免在开发和展示过程中意外拨打真实电话。

CALL\-E 负责电话交互与执行；房地产领域的上下文组织、规划和结果处理仍由本项目负责。

真实拨号、状态查询、录音、转写及取消等能力，应以实际验证的 CALL\-E 接口为准，不将尚未验证的能力描述为已实现。

#### 阶段四：Result Processing — 通话结果分析与 CRM 回填

通话结束后，Agent 将结果转化为业务可用的信息。

当前结果页面重点展示：

**1\. 通话结果概述**

概括客户对房源的态度、主要顾虑、需求变化和后续意愿。

**2\. CRM 字段更新建议**

将客户反馈映射到对应业务字段，包括：

- 两套房源各自的满意点与顾虑。

- 预算、交通、空间等偏好是否变化。

- 客户继续看房或联系经纪人的意愿。

- 仍需澄清的问题。

对于更新建议，保留原值、新值及对应通话证据，避免把推断直接写成确定事实。

**3\. 原始通话证据**

提供可获取的通话转写及录音入口，支持核对结构化结果。

**4\. 业务记忆沉淀**

将经过确认的反馈和偏好变化保存到模拟 CRM 中，使这些信息能够成为后续跟进的上下文。

当前重点完成的是单次回访的结果处理和业务数据回填；完整的自动后续分流尚未实现。

### 4\.3 当前完成情况

以上状态描述的是项目当前报告的功能范围，不等于所有能力都已通过真实电话和真实 CRM 环境验证。

## 5\. 关键产品与技术取舍

### 5\.1 选择业务上下文整合，而不是固定话术模板

固定话术容易实现，但很难体现不同客户的历史信息和当前状态。

因此，本项目优先构建客户画像、历史沟通、带看记录、房源资料与业务知识库的整合能力，再由 Agent 根据经纪人目标生成具体通话计划。

核心价值是让沟通建立在真实业务信息之上，而不是让每个客户经历相同的问答流程。

### 5\.2 选择自主规划，而不是人工配置问题清单

经纪人只需要表达业务目标。

Agent 负责判断需要哪些上下文、哪些信息已经明确、哪些问题值得进一步了解，以及如何组织沟通。

经纪人可以审核任务整体方向，但不需要逐条设计问题。

这一取舍是为了保留 Agent 的自主性，同时让业务人员理解即将发生的电话行为。

### 5\.3 选择稳定的结果结构，而不是每次动态生成不同 Schema

通话内容需要根据客户上下文动态变化，但 CRM 需要稳定、可校验的业务字段。

因此，本项目倾向于由业务代码定义结果 Schema，由 Agent 动态规划收集重点，再将 CALL\-E 返回的信息映射到统一的业务数据结构。

这样既保留沟通灵活性，也有利于后续回填、审计和测试。

### 5\.4 选择 CRM 作为业务记忆载体，而不是另建复杂记忆系统

本项目关注的是跨会话业务记忆，而不是单纯增加向量数据库。

客户画像、房源反馈、需求变化、历史沟通和未解决问题，都可以通过结构化 CRM 数据及历史记录持续保存。

下一次规划时，Agent 重新读取最新上下文，就可以利用此前沟通积累的信息。

这一设计减少了不必要的系统复杂度，也使记忆更容易追溯和维护。

### 5\.5 选择模拟 CRM，而不是优先接入真实 CRM

真实 CRM 接入涉及接口差异、权限、数据合规和部署成本。

在社区示例阶段，这些工作并不能直接证明 Agent 的自主规划和上下文理解能力。

因此，项目先通过模拟 CRM 展示业务数据流和结果回填机制，把开发重点放在可复用的 Agent 设计上。

未来可以替换数据适配层，接入真实业务系统。

## 6\. 产品与技术边界意识

本项目明确区分不同系统的职责。

我认为行业 Agent 不应该把所有能力都放进电话执行层，也不应该重复开发 CRM 已有的客户管理、房源匹配和任务调度能力。

例如，Agent 可以识别客户需要更宽敞且预算内的房源，但不必自行实现完整的房源匹配引擎。

更合理的方式是向 CRM 提供更新后的客户需求，由 CRM 完成匹配，再将匹配结果作为新的事件交给 Agent。

同样，后续任务调度也可以由宿主系统负责，而不是让一次电话执行任务承担长期调度职责。

## 7\. 质量、安全与责任意识

电话 Agent 不仅输出文本，还可能触发真实外呼、改变客户数据并影响后续业务动作。

因此，本项目将安全性和结果可追溯性作为重要设计约束。

### 7\.1 电话执行安全

- 默认使用模拟通话，避免开发过程中产生意外外呼。

- 真实拨号需要明确的人工批准与有效联系许可。

- 拨号前核对客户号码、任务及联系限制。

- 对重复提交设置保护，避免同一计划触发多次拨号。

- 当提交结果未知时，不应直接再次拨打。

- 取消操作只有在电话服务确认后才能视为成功。

### 7\.2 上下文与知识可靠性

- 区分 CRM 中的业务事实、知识库内容和 Agent 推断。

- 对房源实时状态、价格变化等时效性信息保留核实要求。

- 不将历史偏好变化直接解释为客户已确认的新需求。

- 不使用未经验证的政策或交易信息作出承诺。

### 7\.3 结果处理与 CRM 回填

- 结构化更新应尽可能关联原始通话证据。

- 不因客户模糊表达而擅自覆盖精确业务字段。

- 对重要字段变更保留审核机制。

- 对同一通话结果进行重复处理时，避免产生重复更新。

- 客户明确要求停止联系时，应记录联系限制并阻止后续自动外呼。

### 7\.4 人工接管

Agent 可以判断客户可能具有较高购房意向，但不应自行完成议价、交易承诺或最终成交决策。

例如客户提出复看、议价或具体交易条件时，Agent 应将相关意图和证据交给经纪人，由人继续处理。

上述机制包含当前设计原则及后续需要验证的安全要求；未经过测试的部分不应在最终提交中宣称已经实现。

## 8\. 如何验证贡献价值

我认为项目的价值不能仅通过“成功拨通电话”来判断。

更重要的是，Agent 是否真正利用了上下文，是否完成了业务目标，以及结果是否能支持后续行动。

### 8\.1 上下文整合有效性

使用相同的经纪人目标，比较两种情况：

- 不提供历史沟通和业务知识。

- 提供完整的客户上下文和相关知识。

观察 Agent 是否能够识别客户已知需求、历史偏好变化和具体信息缺口，是否减少重复或无关问题。

### 8\.2 自主规划质量

检查生成的计划是否：

- 覆盖本次回访的核心目标。

- 分别收集两套房源的实际反馈。

- 针对已有信息设计合理的确认与追问。

- 避免把推测当作事实。

- 明确执行边界和预期输出。

## 9\. 当前未实现的能力与下一步演进

当前四阶段流程已经覆盖从业务上下文准备、Agent 自主规划、电话执行到结果分析和 CRM 回填的主要路径。

但这还不是完整的持续跟进 Agent。

下一步将重点补充**通话结果驱动的业务分流，以及跨会话自动跟进机制**。

### 9\.1 根据通话反馈进行业务分流

计划支持以下几类结果：

**路径 A：客户希望再次看房**

Agent 识别复看意向，生成看房跟进计划草案，包括目标房源、客户偏好、待确认时间及经纪人需要处理的事项。

具体预约由经纪人或 CRM 确认，Agent 不直接承诺预约成功。

**路径 B：客户对现有房源不满意，但仍有购房需求**

Agent 更新客户需求和房源反馈，将新的偏好交给 CRM 的匹配流程。

例如客户更重视客厅空间、预算仍不超过 500 万，后续匹配应参考这些更新后的条件。

**路径 C：客户有明确购买或议价意向**

Agent 识别高意向信号，整理客户关注的房源、关键诉求及通话证据，生成经纪人优先跟进任务。

**路径 D：客户暂缓或拒绝继续联系**

Agent 记录客户的时间要求或联系限制，避免不合适的后续电话。

### 9\.2 CRM 事件触发下一次电话规划

当 CRM 完成新的房源匹配，或已有跟进任务到期时，向 Agent 提供新的业务事件。

例如：

CRM 发现一套更符合张女士最新预算和客厅空间偏好的房源。

Agent 读取更新后的客户画像、此前两套房源的反馈、新匹配房源资料以及本次事件目标，自动生成新的电话计划。

经纪人确认后，再交由 CALL\-E 执行。

这能够把单次回访扩展为：

**客户反馈 → 业务记忆更新 → CRM 匹配或调度 → Agent 重新规划 → 下一次电话。**

### 9\.3 跨会话记忆与持续目标推进

未来希望进一步支持：

- 持续维护客户需求及其变化历史。

- 保留未解决问题，在后续沟通中适时补齐。

- 根据客户当前阶段调整沟通重点。

- 识别何时需要继续自动跟进、何时应交由经纪人。

- 通过多轮通话逐步推进客户的购房目标。

这里的长期目标不是让 Agent 无限自动拨号，而是在明确的业务授权与工作流约束下，使每次沟通都能继承此前的信息积累，并推动下一步业务行动。

## 10\. 总结

本项目希望探索的不是如何让 AI 多打一通电话，而是如何让电话真正成为业务 Agent 持续工作流程中的一环。

当前实现围绕四项核心能力展开：

1. **Context Integration**：从模拟 CRM、业务知识库及经纪人任务中组织相关上下文。

2. **Autonomous Planning**：由 Agent 自主生成可视化、可确认的电话任务。

3. **CALL\-E Execution**：利用 CALL\-E 完成电话执行流程。

4. **Structured Result \& CRM Update**：将通话结果转化为可追溯的业务信息与客户记忆。

下一阶段将继续探索结果分流、CRM 事件触发和跨会话持续跟进，使 Agent 从完成单次回访，逐步走向围绕长期业务目标自主推进工作。

**我希望通过这个社区示例说明：电话 Agent 的价值不仅取决于对话能力，还取决于它能否理解业务上下文、做出合理规划、沉淀有效信息，并在可控的边界内持续推动业务进展。**
