# Real Estate Buyer Follow-up Agent — Demo 设计方案

> 基于 CALL-E 的上下文感知型房产客户跟进 Agent

## 1. 项目定位与演示目标

### 1.1 项目定位

本项目不是一个完整的房地产 CRM，也不是一个简单的 AI 自动拨号工具。

它是一个基于 CALL-E 的房产客户跟进 Agent，重点展示以下能力：

1. **Context Awareness（上下文理解）**：整合客户画像、历史沟通、带看记录及房源信息，识别需求变化、信息缺口和潜在冲突。
2. **Proactive Planning（主动通话规划）**：根据业务目标和上下文，自主判断本次电话应该沟通什么、优先确认什么。
3. **Business State Update（业务状态更新）**：将电话结果转化为结构化的客户偏好、房源反馈和后续行动，而不是只生成通话摘要。
4. **Human-AI Collaboration（人机协作）**：电话前由经纪人审核，电话后识别需要真人介入的高价值机会。

### 1.2 Demo 核心目标

让观看者在 3–5 分钟内理解：

**Agent 如何从历史上下文出发，自主规划一次有针对性的客户回访，并将电话结果转化为可追溯的业务状态变化。**

不以真实 CRM API 集成能力作为核心展示目标。

### 1.3 Demo 边界

- 使用 Streamlit 构建演示工作台。
- 使用 SQLite 或本地结构化数据模拟 CRM。
- 使用 CALL-E 执行电话。
- 支持 Mock Call 和授权真实拨号两种模式。
- 不开发完整 CRM、房源匹配引擎或复杂任务调度系统。
- 核心 Agent 逻辑与界面代码保持适度分离，方便测试。
- 不强制要求 FastAPI 或真实 CRM 集成。

## 3. Mock 数据设计

第一版只需要一个核心客户、两套房源和三条历史事件。

Mock 数据不应只是填充界面，而应刻意包含需要 Agent 理解和判断的业务信息。

### 3.1 客户基本信息

| 字段 | Mock 值 |
|---|---|
| 客户 ID | C001 |
| 姓名 | 张女士 |
| 城市 | 上海 |
| 客户类型 | 改善型购房 |
| 预算上限 | 500 万元 |
| 意向区域 | 浦东 |
| 户型要求 | 三房 |
| 购房周期 | 3 个月内 |
| 地铁距离偏好 | 初始要求步行 10 分钟以内 |
| 空间偏好 | 客厅宽敞、采光良好 |
| 客户状态 | 持续跟进中 |

所有客户数据均为虚构演示数据。

### 3.2 历史沟通记录

**记录一：10 月 12 日，首次沟通**

客户表示：

> 我主要想看浦东的三房，预算最好不要超过 500 万，离地铁近一点，步行十分钟以内最好。

结构化信息：

- 预算上限：500 万元。
- 区域：浦东。
- 户型：三房。
- 地铁偏好：步行 10 分钟以内。

**记录二：10 月 20 日，第二次沟通**

客户表示：

> 我后来想了想，客厅还是要大一点，住起来舒服更重要。如果房子真的不错，离地铁稍微远一点也可以考虑。

结构化信息：

- 客厅空间的重要性提高。
- 地铁距离可能不再是严格约束。
- 尚未明确可接受的最大距离。

**记录三：10 月 30 日，实地带看**

客户参观了两套房源：

- 房源 A：浦东花园。
- 房源 B：滨江公馆。

带看已完成，但尚未收集详细反馈。

### 3.3 Mock 房源

#### 房源 A：浦东花园

| 字段 | 值 |
|---|---|
| 房源 ID | P001 |
| 总价 | 480 万元 |
| 面积 | 92㎡ |
| 户型 | 三房 |
| 距地铁 | 约 500m |
| 客厅 | 相对紧凑 |
| 带看状态 | 已带看 |
| 客户反馈 | 待收集 |

#### 房源 B：滨江公馆

| 字段 | 值 |
|---|---|
| 房源 ID | P002 |
| 总价 | 530 万元 |
| 面积 | 108㎡ |
| 户型 | 三房 |
| 距地铁 | 约 1.2km |
| 客厅 | 较宽敞 |
| 带看状态 | 已带看 |
| 客户反馈 | 待收集 |

### 3.4 Mock 数据的设计意图

两套房源具有明显的取舍关系：

- 房源 A：符合预算和地铁偏好，但空间较小。
- 房源 B：空间更宽敞，但超出预算，距离地铁也更远。

同时，客户历史沟通已经表明，她对空间和地铁距离的重视程度可能发生变化。

因此，Agent 不应该简单地重复询问预算、区域和户型，而应该围绕：

1. 两套房源的真实反馈。
2. 空间、价格与交通之间的优先级。
3. 客户需求是否发生变化。
4. 是否存在进一步看房或人工跟进机会。

进行通话规划。

## 5. Page 2：Agent 上下文分析与主动规划

这是 Demo 最重要的页面。

### 5.1 页面目标

展示 Agent 不只是拼接资料，而是能够：

- 识别已确认信息。
- 发现历史偏好变化。
- 发现缺失信息。
- 识别潜在取舍和冲突。
- 判断本次通话的重点。
- 形成有针对性的通话计划。

### 5.2 Context Preparation

Agent 输入：

- 当前客户画像。
- 历史沟通记录。
- 历史带看记录。
- 两套房源信息。
- 经纪人本次任务目标。

Agent 输出结构化上下文分析。

建议每项分析包含：

```json
{
  "finding_type": "preference_change",
  "description": "客户对地铁距离的要求可能放宽",
  "evidence": "10月20日：离地铁稍微远一点也可以考虑",
  "confidence": "high",
  "action": "确认可接受的距离范围"
}
```

这里的 `confidence` 只用于表达判断确定性等级，不应伪装成经过校准的统计概率。

### 5.3 预期上下文发现

**发现一：预算已确认**

- 当前预算上限：500 万元。
- 历史记录没有明确证明预算已改变。
- 不需要从零询问预算。
- 但可以在讨论房源 B 时确认预算是否仍为硬约束。

**发现二：地铁距离偏好可能变化**

- 初始要求步行 10 分钟以内。
- 后续表示可以接受稍远。
- 尚未明确最大可接受距离。
- 应进一步确认，而不是直接改写为某个距离值。

**发现三：客厅空间重要性提高**

- 第二次沟通明确强调客厅宽敞。
- 房源 A 的客厅相对紧凑。
- 房源 B 的客厅更宽敞。
- 应重点收集空间方面的实际反馈。

**发现四：两套房源缺少反馈**

- 已完成带看。
- 尚未记录明确评价。
- 需要分别收集，不能混为一条通用反馈。

### 5.4 自动生成通话目标

建议 Agent 生成三个主要目标：

1. 分别收集房源 A、B 的看房反馈。
2. 明确空间、预算、地铁距离的优先级和可协商范围。
3. 判断客户是否希望继续看房，以及是否需要经纪人介入。

### 5.5 自动生成问题计划

示例：

**开场**

> 张女士您好，我想跟您聊聊上次看的两套房子，看看有没有哪些地方比较满意，或者不太符合您的预期。

**问题一：分别收集反馈**

> 上次看的浦东花园和滨江公馆，您觉得各自怎么样？

**问题二：确认取舍**

> 您之前提到比较重视客厅空间，如果客厅更宽敞，但离地铁稍远一点，您现在能接受吗？

**问题三：确认预算约束**

> 滨江公馆的价格比您之前的预算高一些。如果有特别满意的房子，预算还是希望严格控制在 500 万以内吗？

**问题四：确认下一步**

> 如果之后有客厅更宽敞、价格也合适的房源，您还愿意再去看看吗？

### 5.6 规划原则

- 不机械重复已确认的信息。
- 优先询问本次任务所需的关键缺口。
- 多房源反馈必须分别记录。
- 对偏好变化进行确认，不直接推断。
- 不承诺未经确认的房源价格、状态或交易条件。
- 问题计划用于引导自然对话，不要求逐字机械执行。

### 5.7 经纪人审核

界面提供：

- 查看上下文分析。
- 查看判断依据。
- 查看通话目标。
- 编辑或删除建议问题。
- 补充业务注意事项。
- 批准通话。
- 取消本次任务。

经纪人批准前不得触发真实拨号。

## 6. Page 3：CALL-E 通话执行

### 6.1 页面目标

展示 Agent 将规划好的任务交给 CALL-E 执行，并获取通话结果。

### 6.2 执行模式

#### Mock Call

默认模式。

使用预置模拟对话和结果，不产生真实电话费用或外部触达。

用途：

- 本地开发。
- 演示。
- 回归测试。
- 结构化结果验证。

#### Live Call

使用 CALL-E 对授权测试号码进行真实拨打。

要求：

- 显式选择真实模式。
- 经纪人确认通话计划。
- 明确展示目标号码。
- 真实调用所需凭证通过环境变量提供。
- 根据实际 SDK/API 能力管理任务状态。

### 6.3 页面展示

```text
┌──────────────────────────────────────────────┐
│ 通话执行                                     │
├──────────────────────────────────────────────┤
│ 客户：张女士                                 │
│ 任务：看房后回访                             │
│                                              │
│ 模式：[Mock Call ▼]                          │
│                                              │
│ 通话计划：已审核                             │
│ 状态：待执行                                 │
│                                              │
│ [开始通话]                                   │
├──────────────────────────────────────────────┤
│ 执行状态                                     │
│                                              │
│ 待执行 → 已提交 → 进行中 → 已完成             │
├──────────────────────────────────────────────┤
│ 通话记录                                     │
│                                              │
│ Agent：您好，想了解一下上次看房的感受……     │
│ 客户：A 那套位置不错，但是客厅有点小……      │
│ ...                                          │
└──────────────────────────────────────────────┘
```

### 6.4 CALL-E 任务构造

Agent 应将规划结果转换为 CALL-E 支持的实际任务输入。

逻辑上包括：

- 通话目标。
- 必要客户上下文。
- 房源信息。
- 建议问题。
- 不允许做出的承诺。
- 预期结构化结果字段。

具体参数名、任务格式、状态查询和结果获取方式，以实际验证的 CALL-E SDK/API 为准。

不得将未经确认的接口能力写成已支持功能。

## 7. Mock 通话内容

### 7.1 模拟对话

**Agent：**

张女士您好，我想跟您聊聊上次看的两套房子，看看有没有哪些地方比较满意，或者不太符合您的预期。

**客户：**

A 那套位置不错，但是客厅确实有点小。

**Agent：**

明白，您之前也提到比较重视客厅空间。那滨江公馆那套呢？

**客户：**

B 的客厅我挺喜欢的，但 530 万还是超预算了。

**Agent：**

了解。如果客厅更宽敞，但离地铁稍远一点，您现在可以接受吗？

**客户：**

其实地铁远一点也能接受，主要还是房子住着舒服。

**Agent：**

那预算方面，您还是希望控制在 500 万以内，对吗？

**客户：**

对，最好还是 500 万以内。

**Agent：**

明白。如果后续有客厅大一点、价格合适的房子，您还愿意再去看看吗？

**客户：**

可以，有合适的可以再约我看看。

**Agent：**

好的，我会把您的想法整理给经纪人，由他进一步确认合适的房源和看房安排。

### 7.2 设计意图

这段 Mock 对话用于验证：

- Agent 能利用历史信息组织问题。
- 能分别收集房源反馈。
- 能确认需求变化。
- 不会因为房源 B 超预算就擅自提高预算上限。
- 能识别客户仍有后续看房意愿。
- 不会未经授权直接承诺预约。

## 8. Page 4：通话结果与 CRM 更新

### 8.1 页面目标

展示 Agent 如何将通话内容转化为业务状态变化。

不仅展示摘要，还要展示：

- 提取了什么信息。
- 关联到哪个客户或房源。
- 原始值是什么。
- 建议更新成什么。
- 为什么更新。
- 哪些信息不能直接更新。
- 下一步需要谁处理。

### 8.2 结构化房源反馈

**房源 A**

```json
{
  "property_id": "P001",
  "positive_feedback": ["位置满意"],
  "negative_feedback": ["客厅偏小"],
  "overall_interest": "low",
  "evidence": "A那套位置不错，但是客厅确实有点小"
}
```

**房源 B**

```json
{
  "property_id": "P002",
  "positive_feedback": ["客厅宽敞"],
  "negative_feedback": ["价格超出预算"],
  "overall_interest": "conditional",
  "evidence": "B的客厅我挺喜欢的，但530万还是超预算了"
}
```

`overall_interest` 是 Agent 的业务归类，不等于客户明确给出的购买意向等级，界面应保留推断标识。

### 8.3 客户偏好更新建议

| 字段 | 更新前 | 建议更新 | 处理 |
|---|---|---|---|
| 预算上限 | 500 万 | 500 万 | 保持不变 |
| 地铁距离 | 步行 10 分钟内 | 可接受更远，具体范围待确认 | 记录变化，不覆盖精确距离 |
| 客厅空间 | 希望宽敞 | 高优先级偏好 | 建议更新 |
| 房源 A 反馈 | 空 | 位置满意、客厅偏小 | 建议写入 |
| 房源 B 反馈 | 空 | 客厅满意、价格超预算 | 建议写入 |
| 继续看房意愿 | 待确认 | 愿意考虑合适房源 | 建议更新 |

### 8.4 证据管理

每条重要更新应保留：

- 字段名称。
- 原值。
- 新值。
- 来源通话 ID。
- 对应对话证据。
- 判断类型：明确事实 / 推断 / 待确认。
- 更新状态。
- 更新时间。

### 8.5 更新策略

**可自动生成并建议写入：**

- 明确的房源正负面反馈。
- 已确认的偏好变化。
- 明确的后续看房意愿。

**需要谨慎处理：**

- 模糊预算。
- 未量化的距离范围。
- 未明确的购买时间。
- 根据语气推断的购买意向。

**不得直接写入为确定事实：**

- 客户没有明确表达的数字。
- Agent 自行推测的购买承诺。
- 未经确认的预约时间。
- 未核实的交易条件。

第一版可以采用「Agent 提取 → 经纪人审核 → 写入模拟 CRM」的方式，重点保证正确性和可解释性。

### 8.6 更新结果展示

重复处理同一通话结果时，不应产生重复记录。

## 9. 高意向识别与人工接管

### 9.1 设计原则

高意向识别不能只靠积极语气。

需要结合客户的具体行为表达，例如：

- 明确希望复看某套房。
- 主动询问议价空间。
- 表示近期准备购买。
- 主动要求经纪人联系。
- 明确讨论成交条件。

### 9.2 当前 Mock 案例

客户表示：

> 有合适的可以再约我看看。

这说明客户具有后续看房意愿，但不意味着已经确定购买某套房。

因此，本案例不应直接标记为「强成交意向」。

建议输出：

- 意向状态：有继续看房意愿。
- 关注重点：客厅宽敞、总价不超过 500 万。
- 下一步：CRM 重新匹配房源，经纪人确认后联系客户。
- 人工接管：普通后续跟进，不需要立即介入谈判。

### 9.3 额外高意向测试案例

可以增加一个可切换的 Mock 结果：

> B 那套我挺满意的，如果价格能谈到 500 万左右，我这周就想再去看看，最好让经纪人联系我。

预期：

- 识别较高购买意向。
- 关联房源 B。
- 提取价格条件。
- 提取本周复看诉求。
- 生成经纪人高优先级提醒。
- 不自动承诺降价。
- 不自动确认复看时间。

这样可以在不增加完整第二条流程的前提下，展示不同客户表达如何影响后续动作。

## 11. 增加对照展示：普通 CALL-E vs Context-aware Agent

### 11.1 为什么需要对照

如果只展示 Agent 生成计划、拨打电话和更新字段，观看者可能认为这只是对 CALL-E 的简单包装。

因此建议加入一个轻量对照视图，突出上下文理解带来的增量价值。

### 11.2 基础方案

输入：

> 给张女士打电话，了解她上次看房的感受、购房预算和意向。

特点：

- 使用简单任务描述。
- 不主动整合多轮历史。
- 不明确区分两套房源。
- 不特别处理历史偏好变化。

### 11.3 Context-aware Agent 方案

输入同样的业务目标，但 Agent 可以读取完整 Mock 上下文。

生成：

- 分别收集两套房源反馈。
- 重点确认空间与交通的取舍。
- 不重复从零询问预算。
- 对可能变化的偏好进行核实。
- 明确后续看房意愿。

### 11.4 对比维度

| 维度 | 基础方案 | Context-aware Agent |
|---|---|---|
| 历史信息利用 | 简单任务上下文 | 多来源整合 |
| 通话目标 | 通用回访 | 针对性规划 |
| 问题优先级 | 通用问题 | 根据缺口排序 |
| 多房源反馈 | 可能混合 | 明确分别收集 |
| 需求变化 | 不专项处理 | 主动核实 |
| 结果处理 | 通话摘要或结果字段 | 业务状态更新建议 |
| 人工协作 | 视基础任务配置 | 明确审核与交接 |

上述是两种方案的设计差异，不应直接当作实际效果结论。

如果要证明效果提升，需要运行两种方案并记录实际结果。

## 14. MVP 验收标准

### 14.1 上下文理解

给定三条历史记录，Agent 应能够：

- 识别已确认预算。
- 识别地铁距离偏好可能放宽。
- 识别客厅空间重要性提高。
- 识别两套房源反馈缺失。
- 为关键判断提供对应来源。

### 14.2 主动规划

Agent 应能够：

- 根据简单自然语言任务生成针对性目标。
- 区分已知信息和待确认信息。
- 避免明显重复提问。
- 为两套房源分别规划反馈收集。
- 输出可供经纪人审核的计划。

### 14.3 通话执行

- Mock Call 可稳定完成。
- 真实电话必须经过明确授权。
- 真实模式与模拟模式清晰区分。
- CALL-E 实际集成方式经过验证。
- 执行失败时能够显示错误，不伪造成功状态。

### 14.4 结构化更新

- A、B 两套房源反馈正确关联。
- 预算仍保持 500 万。
- 地铁距离的模糊变化不被错误量化。
- 客厅偏好能够更新。
- 后续看房意愿能够记录。
- 每项重要更新有证据。
- 重复处理不会重复写入。

### 14.5 人机协作

- 未经审核不能真实拨号。
- 模糊信息不直接覆盖确定字段。
- 高意向案例能够触发经纪人提醒。
- 不擅自承诺价格、预约或交易条件。

### 14.6 Demo 体验

- 3–5 分钟可以演示完整流程。
- 用户能理解 Agent 为什么提出这些问题。
- 用户能看到电话前后客户数据的变化。
- 不依赖真实 CRM。
- 可以使用 Mock 模式独立演示。
- 能一键恢复初始数据，便于重复演示。

## 17. 核心产品判断

本项目最重要的不是界面复杂度，也不是是否能够接入某个真实 CRM。

真正需要验证的是：

**Agent 是否能够从业务历史中形成有依据的判断，自主规划下一次沟通，并将沟通结果转化为可靠的业务状态变化。**

因此，开发资源应优先投入：

1. 上下文理解质量。
2. 主动通话规划质量。
3. 结构化结果与证据管理。
4. 业务状态更新正确性。
5. 人机协作边界。

Streamlit、SQLite 和 CALL-E 集成都是实现与展示这些能力的手段，而不是项目本身的创新点。
