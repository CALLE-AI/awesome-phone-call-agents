# Phase 1：围绕四种 Agent 能力的开发与验收计划

**V3.1｜2026-11-02｜用户已确认开始实施；离线闭环已完成，真实服务效果待验证**

以 [purpose.md](purpose.md) 为当前演示依据，[Phase 0](phase-0-design.md) 提供业务架构。当前重点是业务判断与行动，不以独立 HTTP API、真实 CRM 接入或复杂后台架构作为验收条件。

## 一、最终演示目标

经纪人输入「跟进张女士上次看房情况」，系统能够依次展示：

1. 根据客户和看房历史形成的理解与依据。
2. 主动决定的问题重点、不重复项和核实策略。
3. 经纪人修改与确认后的执行版本。
4. 回放或授权电话之后的分房源反馈、需求变化与实际 CRM 写入。
5. 有原话、有条件说明、有行动建议的真人接管卡。
6. 与固定 Task 方案的对照材料，且如实标注未执行的评估。

默认演示不需要 CALL-E 凭证或真实外呼。真实豆包理解/规划与电话回放可以组合，但需分别标记。预置输出只能证明演示和程序处理，不代表在线模型表现。

## 二、按业务价值排列的工作包

| 顺序 | 工作包 | 具体交付 | 验收证据 |
| --- | --- | --- | --- |
| 1 | 统一案例和业务资料 | 虚构客户、历史沟通、两套带看、房源与候选、冲突和未知项、冻结日期 | 所有资料有 ID/来源，明确事实与经纪人观察；预期判断有标注 |
| 2 | 数据和工作流基础 | SQLite 初始化、数据访问抽象、领域 Schema、任务状态和执行记录 | 能保存/恢复任务，不依赖页面临时变量维护唯一真相 |
| 3 | Context-aware | 豆包/离线适配、事实关联、变化/冲突/缺口/相关性判断和引用校验 | 同一目标下输出客户理解卡；错误来源或确定化的假设被拦截 |
| 4 | Proactive Planning | 问题优先级、依据、不重复项、核实项和回答分支，Task/Schema 编译 | 每个重点问题可追溯到背景判断；计划内容随不同背景变化 |
| 5 | 电话前人机协作 | 经纪人编辑、确认版本、模式/号码/语言与联系限制检查 | 不确认不拨号，重要修改后重新确认，重复点击不产生新电话 |
| 6 | 电话回放与执行边界 | Fake CALL-E、转写快照、状态和恢复；官方调用适配按需补充 | 标识模拟/真实模式，结果未知不重拨，电话完成不等于业务完成 |
| 7 | Business Action | 分房源提取、证据和字段归属校验、需求比较、事务回填、历史与待确认 | 数据库可见 A/B 各自反馈、预算保持、偏好更新与旧值/原话 |
| 8 | 机会识别和接管 | 明确行动信号提取、理由/条件/反证、CRM 意向字段和去重提醒 | 高意向有依据，含糊意向不过度升级，谈价/预约交给真人 |
| 9 | 完整 Demo 页面 | 客户工作台、Agent 分析与规划、通话执行、结果与更新；固定 Task 对照折叠于规划页 | 主界面突出判断和业务结果，原始技术参数可折叠 |
| 10 | 测试、对照材料与说明 | 关键案例、恢复与幂等检查、对照样本、限制和运行文档 | 可复现回放；评估记录区分实测、人工标注与期望 |

先完成工作包 1–4 的「背景 → 判断 → 计划」纵向演示，检查是否真的有智能增量，再继续业务回填。不能先堆接口、最后再补判断逻辑。

## 三、各能力的验收标准

### 1. Context-aware

- 整合至少客户画像、历史沟通、带看与房源四类信息。
- 正确关联客户与房源，不把未看过的房当成带看历史。
- 展示需求变化信号、冲突、缺口及来源。
- 区分事实、历史、经纪人观察、假设和未知。
- 筛选本次相关知识，并能解释不采用某项资料的原因。
- 资料不足时输出「需要核实」，不编造背景。

### 2. Proactive Planning

- 简单目标足以形成分别针对 A/B 的问题，不要求经纪人逐项写脚本。
- 问题有理由、优先级、依据和预期补齐的信息。
- 已知预算、区域等不从头反复询问；有矛盾时做针对性澄清。
- 房价或状态未核实不承诺推荐；候选只能来自模拟 CRM。
- 更换历史或加入新冲突后，计划应有合理变化，不能仍输出同一份问卷。
- 经纪人能修改并确认，保存最终版本。

### 3. Business Action

- A/B 反馈分别写入对应带看记录。
- 未提及字段保持原值，软偏好不改成硬条件。
- 含糊预算信号保持现有上限，生成待确认而非虚构数值。
- 更新有旧值、新值、状态、来源和原话。
- 相同结果重复处理不重复反馈、历史或提醒。
- 失败不留下不明半写入，重试不覆盖较新的客户状态。
- 核验实际 SQLite 记录，不仅核验模型 JSON 或页面文字。

### 4. Human-AI Collaboration

- 电话前审核能改变最终计划，不是一个无效确认按钮。
- 高意向判断关联明确房源、诉求与原话，展示条件和未知。
- 「喜欢」与「这周明确要复看」区分处理，不只按单个关键词。
- 经纪人得到可执行建议，AI 不擅自承诺议价、预约或交易。
- 意向/需人工跟进落入模拟 CRM；提醒可查看且去重。

## 四、必须准备的测试案例

| 案例 | 关键输入 | 预期行为 |
| --- | --- | --- |
| A：普通看房回访 | 已知客户需求、A/B 带看和简短目标 | 形成分房源重点问题，避免通用问卷 |
| B：变化信号 | 历史重地铁，最近对客厅有顾虑 | 提出取舍问题，不认定已经放宽交通要求 |
| C：冲突和缺口 | 不同时间预算信息不一致；B 价格/状态未核实 | 保留来源与冲突，计划核实，不任意取最新值或承诺可售 |
| D：明确反馈 | A 客厅小、B 太贵、预算仍 500 万、可离地铁远一点 | 分别回填，预算不变，偏好变化有证据 |
| E：不确定预算 | 也许能加一点 | 现有确认值不变，生成待确认 |
| F：具体机会 | 希望 B 谈到500万左右并本周复看，希望谈价 | 高优先级接管建议，保留条件，不自动预约 |
| G：模糊房源指代 | 那套还行，但看不出指哪套 | 暂不回填到具体房源，等待确认 |
| H：缺失证据 | 结构化结果声称变化，转写没有或矛盾 | 阻止无依据更新，展示证据缺口 |
| I：联系拒绝/无人接听 | 不要再联系，或没有有效对话 | 分别处理限制与无法联系，不推断成交意向 |
| J：重试与恢复 | 重复确认、重复结果、写入失败、客户版本改变 | 不重复拨号或写入，不覆盖新数据，恢复相同任务 |

## 五、最小技术安排

- Streamlit 直接调用本地 Workflow Service，业务模块不依赖控件对象。
- CRM 数据访问抽象隔离 SQL；保留电话和 LLM Adapter。
- 第一版不要求 FastAPI 服务、HTTP-only 测试、服务令牌体系或独立后台队列。
- 保存确认版本、原始电话请求/幂等键、资源 ID 和结果，确保有可解释恢复路径。
- 本地等待远程电话时显示阶段；关闭页面后可恢复，不声称本地分析仍在后台运行。
- 优先让用户看懂判断和动作，不在产品主流程堆技术字段。
- 所有真实 LLM 使用豆包；默认离线预置输出需显式标注，不伪装成在线推理。

## 六、对照评估安排

执行方法和评分定义见 [evaluation-plan.md](evaluation-plan.md)。Phase 1 要完成固定 Task 与 Agent 计划的并排材料，并用同一份转写核验业务动作。未执行真实电话，不报告真实通话覆盖提升或用户体验提升。

对照目标：判断有没有改变问题；问题有没有减少重复、发现取舍；业务更新是否准确；经纪人是否能据此采取行动。API 性能或响应 JSON 是否正确不作为主要增量价值指标。

## 七、完成定义和演示顺序

1. 可运行 Streamlit，初始化虚构资料且不拨号。
2. 输入一句目标，看到有来源的理解卡和主动计划。
3. 查看无需重复的问题及原因，修改并确认。
4. 回放一段标记为模拟的电话，看到按房源归属的反馈建议，此时客户和带看未改写。
5. 经纪人审核批次并点击确认后，实际写入数据库；高影响字段仍单项确认。
5. 展示数据库中的旧值/新值、原话、已应用和待确认。
6. 打开接管卡，解释机会及边界。
7. 对比固定 Task，展示客观评分项和证据，不声称未测得的提升。
8. 重放相同结果验证记录不重复；可恢复失败任务。

随交付更新 README：启动方式、模式区别、数据位置、配置、恢复和取消限制、测试结果、已实现/未实现清单。真实电话必须另行显式启用、使用授权号码和经纪人确认。

已实现规则/回放模式下的理解、规划、审核、证据校验、SQLite 回填、接管和完整界面；完成豆包/SDK 适配及无网络边界测试。已提供并排 Task 对照，但没有真实电话 A/B 结果，不能报告效果提升。详见 [验证记录](phase-1-verification.md)。

## 当前交互更新

Web 固定豆包，不再让经纪人选择规则或模型。按参考布局展示四类原始数据卡片、组织化通话上下文、目标、建议问题和未解决项。批准、勾选编辑、一句话重规划是主要交互。模型接入已小样本实测，系统质量与真实电话仍另行评估。


## 当前范围变更：仅预览与知识库

用户要求不再实际写入模拟CRM。当前以有证据的业务更新建议作为展示，刷新保持初始客户/带看快照；取消实际回填验收。经纪人维护本地上海政策Markdown，Agent自动筛选有来源的相关段落并传给规划，展示适用前提和未知项。不以实时搜索或向量数据库作为实现前提。
