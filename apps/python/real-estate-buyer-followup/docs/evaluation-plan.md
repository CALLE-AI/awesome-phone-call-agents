# 固定 Task 与 Agent 的对照评估方案

**V3.0｜2026-11-02｜实验设计，尚无实验结果**

## 一、要回答的问题

1. 上下文理解是否带来了更有针对性、证据正确的问题？
2. 主动规划是否减少重复、优先澄清真正影响决策的事项？
3. 业务动作是否能准确反映反馈与变化，而不是仅生成总结？
4. 人机分工是否能找到具体机会，同时保留条件和不确定性？

不以 API 是否成功、计划文字更长、生成问题更多或给出更高意向标签作为价值指标。

## 二、基线如何设置才公平

### 主要对照

| 条件 | A：固定 Task | B：Agent 准备后的 Task |
| --- | --- | --- |
| 客户与目标 | 同一个虚构客户与经纪人目标 | 相同 |
| 原始背景 | 相同客户、历史、带看和房源数据，按固定模板直接附加 | 相同原始数据，由 Agent 关联、筛选并形成判断 |
| 计划生成 | 通用固定问题与规则，不做显式的变化/冲突/缺口分析 | 形成沟通方向、业务优先级、不重复项和条件策略 |
| 电话服务 | 相同 CALL-E 接口及可控制的语言/运行条件 | 相同 |
| 结果 Schema | 相同字段、未知回退约定与约束 | 相同 |
| 评价 | 同一评分表、相同场景的标注事实与新反馈 | 相同 |

A 不是故意做差：至少包含任务、相关原始资料、合理通用问题、明确身份/边界和结果字段。CALL-E 自身可能从资料中推断出重点，这也是应观察的真实基线表现。B 的收益需要实测，不能预设它必胜。

可另展示 A0「只有一句目标」帮助理解，但 A0 因缺少背景，不能用它单独证明 Context Preparation 的加工能力。主要证据来自 A 与 B 的比较。

### 明确处理两个混杂因素

- 若 B 比 A 使用更多资料、不同结果字段或更长通话预算，须单独记录，不能把差异全部归因于 Agent 的判断。
- 如果 B 的整个产品流程包含 CRM 写入而 A 没有，只能说明产品功能范围不同，不能证明 CALL-E 不支持结构化结果。应另做同转写下的业务动作测试。

## 三、分三层验证，分别报告结论

### 第一层：离线计划质量

准备原始背景、来源标识、经纪人目标、允许得出的结论和不应推断的事项。生成或整理 A/B 任务，逐项检查覆盖、重复、依据和不确定性。

检查点例如：A/B 分别收集反馈；交通与空间的取舍尚未确认；预算已确认时不从头重复；不把房源事实核对交给客户；不存在的候选不推荐。

这层可以评价计划，但不能证明真实电话一定按计划执行或体验更好。

### 第二层：同转写下的业务动作正确性

向相同的结果处理模块提供同一份虚构转写和相同结构化结果，验证实际数据库反馈、需求变化、待确认和接管建议。

- 预先人工标注应更新、应保持、不确定和必须接管的事项。
- 对比字段、房源、证据、历史和提醒是否正确。
- 使用相同转写隔离提取/执行能力，不把回放包装成通话 A/B 实验。
- 如果对比「简单映射」与「证据校验」两个业务处理器，必须明确它们都是本地实现，不代表 CALL-E 的全部能力。

### 第三层：可选真实通话

只有取得授权、可用账号和经纪人确认后才执行。使用测试参与者及固定场景说明；参与者拥有应提供的事实，但允许随问题自然回答，不能向 A 隐瞒、向 B 主动提供答案。

尽可能固定电话配置、语言、角色要求、时长目标、结果 Schema、参与者回答规则。CALL-E 未暴露可调参数时记录为不可控，不声称底层模型完全一致。

A/B 使用独立会话，交替顺序，记录次数和执行时间。人工审核两组均可修正明显事实错误，但记录修正内容；主要对照不为 B 额外补充正确答案。真实电话的差异需结合随机性解释，少量演示只能说明案例，不能推断普遍提升。

## 四、评价维度、分母和证据

| 维度 | 怎么评分 | 需要的证据 |
| --- | --- | --- |
| 重点覆盖 | 已覆盖必需检查项 / 预先定义的必需检查项；计划覆盖与电话实际获取分开 | 问题或转写位置，对应标注项 |
| 重复询问 | 不必要的重复问项数量及对应问项；不把有理由的冲突澄清计为重复 | 已确认历史与实际问题；出现新矛盾时说明豁免理由 |
| 需求变化处理 | 正确确认变化、正确保留未知、误改和漏改分别计数 | 人工标注、字段变化、原话 |
| 结构化结果 | 字段和房源归属的正确性、证据有效性；程序解析成功另记 | Schema 结果、转写、viewing/property ID |
| 后续行动 | 是否有依据、具体且适合真人处理的建议；是否越权 | 行动卡、支持/反向证据、是否作了未经确认的承诺 |

「问得多」不等于覆盖好；「意向更高」不等于识别更准。没有变化的案例也必须正确保留旧值，明确记录误改次数，避免只报告成功更新数。

电话没接通或客户未提供证据时，不填成 negative；标记不可评估并报告数量和原因。汇总时同时报告总样本数、有效样本数和每项实际分母。

## 五、最小场景集

1. 正常分房源反馈和明确软偏好变化。
2. 预算含糊、但没有确认新上限。
3. 历史资料冲突或房源状态过期。
4. 明确复看诉求与有条件的议价兴趣。
5. 模糊房源指代或转写缺失，不能强制归属。
6. 拒绝联系或无人接听，不能推断为低购房意向。

先冻结评分规则与期望，再运行方案。避免看完 B 的输出后才挑选有利指标。至少有一个新措辞或新冲突案例不用于调提示词，检查是否只记住演示答案。

## 六、实验记录结构

每条记录保存：case_id、原始数据版本、目标、方案 A/B、Task 版本、理解卡/计划版本（如有）、真实/回放/人工整理模式、豆包模型与配置（如使用）、CALL-E 可控参数、执行时间、审核修改、结果/转写引用、逐项评分、评分人和备注。

原始转写与任务内容属于证据，模型写出的总结不能替代。公开仓库只提交虚构或适当脱敏的材料，不包含真实号码、私有转写或凭证。

## 八、Phase 1 应交付什么

- 一份同源背景及评分标注。
- 固定 Task 和 Agent 计划的并排对照，能看到问题为何变化。
- 同转写业务更新的程序验证与实际 SQLite 记录。
- 已测、未测、模拟和模型输出之间的明确标记。
- 如条件允许，补充授权下的豆包理解/规划评估；真实电话测试独立列示，不作为离线闭环前置条件。

不要求为了实验开发分析看板或通用评测平台，先用固定案例、JSON 记录和 Markdown 报告即可。
