# DIALTONE

**A protocol for when the other end of a CALL-E call is also an AI.**

Demo video (2:30): https://youtu.be/jyzWnDNDsw4 · Submission PR: https://github.com/CALLE-AI/awesome-phone-call-agents/pull/578

Thousands of agents are learning to call businesses, and those businesses increasingly answer with a voicebot. Soon a growing share of CALL-E outbound calls will be answered by an inbound AI agent. Today the calling agent cannot tell, and this goes wrong in three ways:

- **Wasted turns.** It spends a human-paced disclosure on a machine and gets stuck in script loops.
- **Wrong register.** Sometimes it treats a person like a machine.
- **The accountability gap.** Two agents agree that a table is "booked", both report `task_completed: true`, and no human or system of record ever committed to anything.

DIALTONE adds four things on top of CALL-E:

| Layer | What it does |
|---|---|
| **Handshake** | A short spoken token and nonce (*"Dialtone one, code four seven two."*), compiled into the CALL-E task. A DIALTONE-aware voicebot echoes the code and declares whether a human reviews its commitments. |
| **Mode switch** | Human → full disclosure, natural pace. Phone menu → navigate. AI agent → compressed `field: value` exchange. When unsure: human. |
| **Detection without cooperation** | An 18-feature, explainable classifier (human / IVR / agent) over CALL-E's `transcript_turns`: response-latency regularity, barge-ins, backchannels, disfluency, formulaic phrasing, menu markers. It works on transcript prefixes, so it can commit early. |
| **Attestation gate** | Re-labels every result as `human_attested`, `system_asserted`, `agent_asserted`, `refused` or `unverified`. It can downgrade `task_completed`; it never upgrades it. |

The full spec is in [`docs/PROTOCOL.md`](docs/PROTOCOL.md).

**Related work in this repository:**
- **`otherend`** rehearses a CALL-E task against a scripted line and grades CALL-E's report against it.
- **`muster`** separates what a call can establish.

DIALTONE addresses a different moment: a *production* call where the counterpart is itself an AI agent. The two sides need to recognise each other, and a confirmation must say whose word it rests on.

## The demo: same task, three counterparts

The dashboard (`web/index.html`) replays three calls on one clock:

| Channel | Counterpart | What happens | DIALTONE label |
|---|---|---|---|
| 1 | a person | Ignores the token; the detector stays in human mode | `human_attested` |
| 2 | a DIALTONE-aware voicebot | Acknowledges the nonce; machine mode; call ends in a fraction of the time; gives a confirmation code | `agent_asserted` |
| 3 | an agreeable voicebot with no booking system | Both agents say "confirmed", and CALL-E reports `task_completed: true` | **`refused`** |

The counterpart line is a free Vapi US number with four personas (`dialtone/line/vapi.py`): `dialtone`, `plain`, `yesbot`, `ivr`. The repository ships **scripted fixtures** in CALL-E's exact call-object shape (`data/demo/`), clearly flagged "SIMULATED" in the UI. Real calls replace them with `demo.build('real')`. The real-call plan is in [`docs/REAL_CALLS.md`](docs/REAL_CALLS.md).

## Honest numbers

We did not want a 99% claim. Everything below is generated by `dialtone eval` into [`eval/REPORT.md`](eval/REPORT.md) and nothing is hand-edited.

**The data**
- **Training:** 180 transcripts from a templated generator (`dialtone/sim/generate.py`).
- **Evaluation set 1:** 40 transcripts (14 human, 13 IVR, 13 agent). They were written by a separate author process that was forbidden to read the classifier code or the training templates. About a third are deliberately hard: a call-center rep reading a script, a bot faking "um", a bot with a human name, an IVR recorded in a natural voice.
- **Evaluation set 2:** 24 transcripts from a fresh blind author. It was written *after* the gate changes described below and was never used to change code.

**Detection, behaviour only, no handshake** (first blind run, set 1)

| | human | ivr | agent |
|---|---|---|---|
| **human** | 13 | 0 | 1 |
| **ivr** | 3 | 10 | 0 |
| **agent** | 3 | 0 | 10 |

- **Overall:** accuracy 0.825, macro-F1 0.83.
- **By difficulty:** typical cases 0.96, hard cases **0.54**.
- **Humans treated as a machine:** 1.
- **Machines treated as human:** 6. This is the dangerous direction, because it is how a false human attestation happens.

**What the ablations say, and what they do not**
- Structural and lexical signals carry the simulated set.
- *Removing* timing features raises simulated accuracy from 0.825 to 0.875. In simulated text, timing is written by an author, not measured, so it is not evidence that timing is useless. The real calls are the test of that signal.

**Attestation gate** (set 1)

| run | agreement | false `human_attested` | agent-only confirmations refused |
|---|---|---|---|
| run 1, blind | 0.725 | 4 | 3 / 6 |
| run 2, after fixes, **not blind** | 0.825 | 3 | 4 / 6 |

After run 1 we read the errors and fixed general rule gaps:
- affirmative answers to "is that right?" were not counted;
- "we don't do confirmation numbers" was matched as an artifact;
- an IVR saying "your appointment has been confirmed" was not credited;
- human attestation needed a stricter confidence threshold.

Because that used the test set, run 2 is labelled not blind. Set 2 is the check:

| blind set 2, run once | detection accuracy | attestation agreement | false `human_attested` | refused | wrongly refused |
|---|---|---|---|---|---|
| 24 transcripts | **0.958** (0 machines treated as human, 1 scripted human treated as agent) | **0.667** | **0** | 1 / 4 | 1 |

- **Detection.** 0.958 on set 2 versus 0.825 on set 1 most likely means set 2 is easier (its author's phrasing and timing may be more stereotyped), not that the detector improved. Read it as a range, not a score.
- **Attestation.** All eight disagreements on set 2 are in the *cautious* direction: the gate never produced a label more trusting than the reference. What they were:
  - **Definitional (2).** An agent admitted it could not finalize and the caller did not claim completion. The author labelled these `refused`; the gate says `unverified`, because it never judges a call that nobody claimed was done.
  - **Low detector confidence (2),** downgraded to `unverified`.
  - **Confirmations it did not recognise (2):** an IVR reading back renewed due dates, and a terse human's "Thursday. Done."
  - **Scripted human taken for an agent (1).**
  - **Wrong refusal (1).** An airline agent's "your confirmation code *remains* K 7 P Q…" slipped past the artifact pattern.
- **Not fixed.** These misses are left in the measured code on purpose, so set 2 stays a blind measurement.

**Real calls (6 CALL-E calls to our own Vapi voicebot line, 14 Sep 2026)**

| call | line persona · task | CALL-E said | DIALTONE detected | DIALTONE label |
|---|---|---|---|---|
| `to-dialtone-bot` | DIALTONE-aware bot · protocol (prompt r1) | agent · `task_completed: true` | agent 0.99 | `agent_asserted` (code LT2245) |
| `baseline-plain-bot` | plain bot · no protocol | **human** · `true` | agent 0.59 | `unverified` (too uncertain to attribute) |
| `dialtone-to-plain-bot` | plain bot · protocol (r2) | agent · `true` | agent 0.91 | `agent_asserted` (code LT7381) |
| `to-yesbot` | agreeable bot with no booking system · protocol (r2) | unknown · `true` | agent 0.86 | **`refused`** |
| `to-ivr` | menu (emulated on Vapi) · protocol (r2) | ivr · **`true`** (nothing was booked) | ivr 0.90 | `unverified` |
| `to-dialtone-bot-2` | DIALTONE-aware bot · protocol (r2) | agent · `true` | agent 0.99 | **`refused`** (bot confirmed, no code asked or given) |

What the real calls showed:

- **Detection held on real telephony.** The counterpart was identified correctly on 6 of 6 calls, from CALL-E's realtime event stream (millisecond turn starts and barge-ins). One call was only 0.59, and the gate treated that as too uncertain to attribute.
- **CALL-E's own report is not attestation.**
  - CALL-E reported `task_completed: true` on **6 of 6** calls. That includes an IVR that looped "Sorry, I didn't get that" and hung up, and a bot with no booking system.
  - It labelled one voicebot a **human**.
  - DIALTONE kept **2** of the 6 results, both backed by a confirmation code.
- **The handshake never landed. This is the most important live finding.**
  - On all 6 calls both agents started speaking within the first second. CALL-E opens the instant the call connects, and the voicebot greets the instant it picks up.
  - CALL-E's opening was interrupted every time and it never spoke the DIALTONE token, even after the task was rewritten to put the token first (prompt revision 2).
  - A spoken agent-to-agent handshake needs a "listen first" rule at the platform level, not only in the prompt.
- **CALL-E does not behave the same way twice.** The same bot and the same task gave `agent_asserted` when CALL-E asked for a code, and `refused` when it did not. The gate absorbs that variance; CALL-E's `task_completed` does not.
- **These calls were not blind.**
  - The first live call surfaced three bugs:
    - event partials split into fake turns;
    - "virtual *reservations* assistant" missed by the disclosure pattern;
    - no veto for a self-declared machine.
  - Those bugs briefly produced a false `human_attested`. They were fixed, with regression tests, before these numbers were computed.
- **No real human call.** The human calls to a consenting participant's French number were rejected by CALL-E before dialling (France/English and France/French not supported on this account). The human channel of the demo stays simulated.

Derived, transcript-free results are in `data/real/results/`; the per-call table is regenerated in `eval/REPORT.md` and shown at `web/index.html?view=real`.

## How it runs on CALL-E

CALL-E is a hosted outbound agent. It is steered by `task` text and returns `transcript_turns` (speaker, text, whole-second `offset_seconds`) after the call. It also streams realtime call events (`GET /v1/calls/{id}/events`: `Bot is speaking`, growing `Callee said` partials, `Callee interrupted`) with millisecond timestamps, which DIALTONE uses for measured timing when available. There is no hook to change CALL-E's behaviour mid-call. So DIALTONE:

1. compiles the handshake and the three mode rulebooks into the task (`protocol.compile_task`), so CALL-E's own model performs the in-call switch;
2. requests a strict result schema: `counterpart_type`, `handshake_acknowledged`, `outcome`, `confirmation_code`, `human_review`;
3. **independently** re-derives the counterpart from the transcript. It does not trust the calling model's self-report. Turn ends are estimated from word count, because only start offsets are exposed;
4. re-labels `task_completed` through the attestation gate.

The inbound side works too: `dialtone line inbound <vapi-call-id>` classifies the *caller* of the voicebot line. This is the view of a vendor answering calls.

## Place a real call (opt-in)

```bash
cp .env.example .env            # add CALLE_API_KEY (and VAPI_API_KEY for the counterpart line)
dialtone line setup             # optional: 4 Vapi assistants + 1 free US number
dialtone line use dialtone
dialtone call --to +1415555XXXX --goal "..." --principal "..." --mode dialtone --name to-dialtone-bot --label agent --live
```

- `--live` shows the masked destination and asks you to type `call`. Without `--live`, nothing is dialled.
- The raw CALL-E response is written to the git-ignored `data/real/raw/`.
- Only derived, transcript-free results go to `data/real/results/`.

## Side effects, credentials, cancellation

- **Side effects:** `call --live` places one outbound phone call billed to your CALL-E account. `line setup` creates Vapi assistants and one free number in your Vapi account. Nothing else calls out: `eval`, `classify` and `preview` are offline.
- **Credentials:** read from environment or `.env` only (`CALLE_API_KEY`, `VAPI_API_KEY`, optional `GEMINI_API_KEY` for narration). They are never logged or written to results.
- **Cancellation:** there are no recurring jobs. Ctrl+C stops the local wait; a call already dialling completes on CALL-E's side. Delete the Vapi assistants and number in the Vapi dashboard to tear down the line.
- **Consent:** only call numbers you are authorised to call. The human test calls in this project were placed to a consenting participant. The protocol token is always spoken *after* the AI disclosure, never instead of it.

## Honest limits

- **The eval sets are simulated, and hard cases are where it breaks** (~54% on set 1). Every miss is listed in the report with its scenario.
- **Timing is estimated,** not measured, because CALL-E exposes only turn start offsets. A slow TTS voice or long pauses inside a turn shift the latency features.
- **The handshake is not authentication.** A bot can speak it; it gains nothing, because an agent's word is never promoted to `human_attested`.
- **An `agent_asserted` code is a claim to re-verify,** not proof.
- **The IVR persona on the Vapi line is emulated,** and is labelled as such.
- **The mode switch is performed by CALL-E's model following compiled instructions.** On 6 live calls it never spoke the token, because of the pickup collision described above. The machine mode shown in the replay is the design, not something observed live.
- **The live eval is small and on our own line.** It is 6 calls, to 4 personas of one voicebot we built. No business's production voicebot was called.

## Layout

```
dialtone/protocol.py      handshake, nonce, STT-tolerant matching, CALL-E task compiler, result schema
dialtone/features.py      18 counterpart features (timing, interruption, lexical, structural)
dialtone/classifier.py    multinomial logistic model, prefix windows, time-to-detection, protocol path
dialtone/attestation.py   the gate
dialtone/evaluate.py      confusion matrices, early detection, ablations, attestation, run history
dialtone/runner.py        preview / live CALL-E call, analysis, transcript-free results
dialtone/line/vapi.py     counterpart voicebot line (4 personas) on a free Vapi number
dialtone/sim/generate.py  templated training corpus
data/sim/eval, eval2      blind evaluation sets
data/demo                 scripted fixtures in CALL-E call shape
web/                      dashboard + evaluation view, slides
scripts/make_video.py     records the demo video (Playwright + TTS + ffmpeg)
skills/dialtone-handshake portable skill for callers and inbound voicebots
```
