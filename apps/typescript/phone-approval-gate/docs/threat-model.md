# Threat model

A phone call is a strong way to reach a person and a weak way to prove who they
are. This document says exactly what the gate establishes, what it does not, and
where an operator has to add something else.

## The two channels

The gate uses two channels on purpose.

```text
request channel   the pipeline, the agent transcript, the change ticket
                  carries the change text and the one-time code
voice channel     the CALL-E call to an enrolled handset
                  carries the decision and the code coming back
```

In the default `code_from_request` binding, the code is generated by the gate,
printed on the request channel and never spoken by the caller. To approve, the
person has to return it over the voice channel. That is the out-of-band pattern
described in NIST SP 800-63B, Authenticators and the gate follows the same
constraints:

| SP 800-63B requirement for an out-of-band secret | What the gate does |
| --- | --- |
| "at least six decimal digits (or equivalent) in length" from an approved generator | six digits from `crypto.randomInt` or three words from a 128 word list, which is about 21 bits or 6.3 decimal digits |
| "Verifiers SHALL accept a given authentication secret as valid only once during the validity period" | one secret per approver per request, never reused across attempts |
| "the authentication SHALL be considered invalid unless completed within 10 minutes" | `window_seconds` is capped at 600 and the request file cannot ask for more |
| rate limiting on short secrets | `max_failed_attempts` stops the ladder and the gate never re-dials the same approver automatically |
| compare-and-approve prompts are "no longer considered acceptable" because of authentication fatigue | a bare yes is not an approval, the secret has to come back |

That last row is the reason this is not a "press 1 to approve" system. A person
who is called at midnight and asked a yes or no question will say yes. A person
who has to read back a code from the change request has to look at the change
request.

## What the gate establishes

1. **A live person was on the line.** The decision comes from recipient turns in
   the transcript, not from a summary and voicemail greetings and menu prompts
   are treated as machines. A recorded yes cannot pass the code check.
2. **That person could see the request.** Returning the code shows access to the
   request channel, so an approval is bound to one specific change and not to a
   vague question about deploying.
3. **The call reached an enrolled handset.** The gate only dials numbers listed
   in the request file with an `enrolled_at` date and an `authorized_for` scope
   that covers the environment.
4. **The decision is recorded with its evidence.** The record holds the inputs
   the outcome was computed from plus the CALL-E `call_id` and the provider call
   id, so an auditor can reconcile it against the CALL-E side independently.

## What the gate does not establish

Read this list before putting the gate in front of anything expensive.

| Threat | Position |
| --- | --- |
| Someone else answers the enrolled handset | Not prevented. Possession of the handset is the only identity factor. Use `mode: dual` for changes where that matters and keep the window short. |
| SIM swap, number porting, call forwarding | Not prevented. SP 800-63B names "device swap, SIM change, number porting" as signals a verifier should weigh and the gate cannot see any of them. Treat re-enrolling a number as a security event. |
| Voice cloning of the approver | Not addressed. The gate scores what was said, not who said it. Voice is not treated as a biometric anywhere in the code. |
| A pipeline that never calls the gate | Out of scope. A gate cannot defend a workflow that skips it. Put the gate step in a protected environment and require review on the workflow file itself. |
| A compromised runner that fabricates a whole run | Partly detectable. The hash chain catches edits to existing records and the recorded `call_id` and `provider_call_id` let an auditor confirm the call exists on the CALL-E side. A record with no matching CALL-E call is the signal. |
| The person on the call is coerced or socially engineered | Out of scope, as it is for every approval mechanism. |
| Someone with CI log access reads the code | Accepted. The code binds an approval to a request. It is single use, it expires with the window and anyone who can read the log can usually read the change anyway. It is not an identity secret. |
| Guessing the code | Six digits, capped failed attempts and a ten minute window. |
| Instructions injected during the call | The call script refuses every request other than this one approval and the gate treats transcript text as evidence to read, never as an instruction to follow. |
| Change details left on a machine | The script ends the call on voicemail or a menu system without describing the change and without leaving a message. |

## PSTN is a restricted channel

SP 800-63B is explicit: "Use of the PSTN for out-of-band verification is
restricted." Restricted means usable with eyes open, not forbidden and the
publication asks the party accepting it to weigh the risk, notify people about
it and keep a non-restricted alternative available.

So the honest framing for this gate is: it is an authorization control with an
evidence trail, not an identity proof. It answers "did a person who holds the
enrolled handset and can see this request say yes to this exact change and can
we show that later". It does not answer "was that person definitely Alice".

For changes where the second question matters, pair the gate with something the
phone cannot give you: dual control across two handsets, a hardware second
factor on the request channel or a person present in the room.

## Change control context

The record exists because approving a production change is usually a documented
control, not a courtesy. NIST SP 800-53 Rev 5 CM-3 asks an organization to
"review proposed configuration-controlled changes to the system and approve or
disapprove such changes", to "document configuration change decisions associated
with the system" and to retain those records. `mode: dual` maps to AC-3(2) Dual
Authorization, which the catalog also calls two-person control and describes as
requiring "the approval of two authorized individuals to execute".

The gate produces the artifact those controls ask for as a side effect of doing
the useful thing, which is reaching a person who was not at a keyboard.

## Data handling

Stored in a record:

- approver id and the phone number masked to country code plus the last two digits
- CALL-E `call_id` and provider call id
- the decisive recipient turns, with the code or phrase replaced by `[code]` or `[phrase]`
- digests of the expected secret and of what was spoken, salted with the request id
- the inputs the outcome was computed from and the outcome

Not stored:

- the full phone number
- the full transcript
- the code or phrase in plain text
- the API key, which the gate only reads from the environment

Records are appended with mode `0600`. Rotate and retain them the way your change
management policy already says to.
