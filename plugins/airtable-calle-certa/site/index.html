Boundary one

A filled-down cell is not consent

Ticking one checkbox and dragging it down a column would authorise every row it touched. So consent is a hash of the row’s own content — a copied token was derived from a different number, and is refused.

       | spec_version | receipt_id)
Boundary two

The applicant’s number is never dialled

Fraudulent applications supply working numbers, with staffed call centres and directory listings. It is the one field an applicant fully controls, and the manual process calls it anyway.

Who actually makes these calls.

Verification of employment is not a niche. It is a step somebody performs by phone, every working day, because the answer lives with a person rather than in a database.

Lending

Before a loan closes

An underwriter must confirm the applicant works where the application says. For large employers a payroll database answers. For everyone else — small firms, contractors, most of the world outside the US — somebody calls HR and waits.

Certa runs the queue from the view the underwriter already works in, and refuses any row whose employer number came from the applicant.

Tenancy

Before a lease is signed

A letting agent checks that a prospective tenant is employed and earning consistently enough to cover rent. The check is nearly always a phone call to an employer the applicant named.

The applicant naming the employer is exactly why the number must be sourced independently. That is a boundary, not a setting.

Background screening

Before an offer is confirmed

Screening firms verify claimed employment history for candidates. Volume is high, the questions are fixed, and the work is almost entirely hold music.

Three questions, eight prohibitions, a typed answer per row, and an audit record of who was called under which consent.

Immigration

Before a filing goes out

Employment letters get verified by phone against the employer named on the filing. A refusal to confirm is a real and acceptable outcome that has to be recorded as one.

A refusal ends the call and is terminal, never retried. Redialling somebody who declined is harassment, and the code treats it that way.

The same shape every time: a third party who did not ask to be called, a consent that has to be provable, a short bounded set of questions, and an answer that must be typed rather than transcribed.

Enforced by construction, not by policy.

Types that cannot be built the wrong way, with tests that fail if that ever stops being true.

Fails closed, always
Low confidence, a positive claim with no supporting evidence, or any internal contradiction all route to a human. No rule can promote a result.
Nothing reachable from outside
The console binds loopback only and needs a one-off token the app generates for itself. Its run endpoint accepts a view name — never a destination — so no request can introduce a phone number.
Numbers are never repaired
Strict E.164, with no inferred country code. A malformed number is a data problem for a person, not something to guess at.
Masked everywhere
Last four digits only — console, logs and audit records alike. Consent tokens are stored as a prefix: enough to correlate, not enough to replay.
Re-running never re-dials
The idempotency key binds the request, the exact number, the question set and the consent. Re-consenting after an edit correctly creates a new intent.
